# 2. Plan

Explore 단계에서 파악한 요구사항과 프로젝트 상태를 바탕으로 작업 계획을 세워라. 이 계획을 모두 이행하면 요구사항이 모두 충족되어야 한다. 이 단계에서는 코드를 수정하지 않는다.

공통 규칙은 `sdd-workflow` 스킬을 따른다.

## 입력

- `$TASK_DIR/00.explore/EXPLORE.md` ("관련 중앙 문서" 절 포함)

## 절차

1. `$TASK_DIR/01.plan/`을 만들고 타임라인을 기록하라.
   ```bash
   node .claude/skills/sdd-workflow/scripts/timeline.mjs mark "$TASK_DIR" plan - start
   ```
2. `EXPLORE.md`를 읽어라. 계획에 필요한 사실이 빠져 있으면 해당 파일만 추가로 확인하라.
3. **인수 조건 정의** — `ACCEPTANCE_CRITERIA.md`
   - EXPLORE.md의 요구사항(R-xx)마다 하나 이상의 인수 조건(AC-xx)을 만들어라.
   - 인수 조건은 관찰 가능하고 합격/불합격이 갈리게 써라. "잘 동작한다", "개선된다" 같은 표현을 쓰지 말고 조건, 행동, 기대 결과를 적어라.
   - 요구사항에 없는 기능을 인수 조건에 넣지 마라. 범위 밖으로 둔 항목은 "범위 제외"에 적어라.
   - 이 문서는 Plan 단계 이후 수정할 수 없으므로 빠진 것이 없는지 요구사항 추적표로 확인하라.
4. **인수 테스트 계획** — `ACCEPTANCE_TEST_PLAN.md`
   - 인수 조건마다 이를 검증할 인수 테스트(AT-xx)를 하나 이상 정의하라. 모든 AC가 최소 하나의 AT에 매핑되어야 한다.
   - 테스트마다 사전 조건, 수행 절차(실행할 명령이나 조작), 기대 결과, 증거 수집 방법을 적어라.
   - 실제 사용 방식대로 검증하라. 데몬·CLI라면 실제로 실행해 출력·로그·DB 상태를 확인하고, UI가 있으면 화면을 조작해 스크린샷을 남긴다.
   - 단위 테스트·통합 테스트는 계획하지 않는다. 빌드·타입체크·린트 통과가 인수 조건이면 그것을 실행하는 절차를 인수 테스트로 둔다.
   - 테스트 환경(Host OS / Docker, 필요한 서비스, 환경변수)을 명시하라.
5. **작업 계획** — `PLAN.md`
   - 전체 작업을 작은 단위 작업으로 쪼개 수행 순서대로 번호 목록으로 적어라.
   - 단위 작업마다 변경 대상(파일·모듈), 할 일, 완료 기준, 관련 AC를 적어라.
   - 단위 작업의 완료 기준을 모두 채우면 모든 AC가 충족되어야 한다. AC 추적표로 확인하라.
   - 선행 관계가 있으면 순서에 반영하고, 위험 요소와 대응을 적어라.
6. **중앙 문서 최신화 계획** — `PLAN.md`의 "중앙 문서 최신화" 절
   - 이 계획은 Verification Gate 통과 후 Documentation 단계(`sdd-documentation`)가 수행할 대상 목록이다. Implementation 단계의 단위 작업으로 넣지 마라. 검증된 형상만 문서에 반영하기 위해 문서 최신화는 검증 뒤에 수행한다.
   - `EXPLORE.md`의 "관련 중앙 문서"를 바탕으로, 이번 작업으로 내용이 달라지는 `docs/` 문서를 정하라.
   - **이미 있는 문서만 대상으로 삼아라.** 없는 문서를 새로 만드는 계획을 세우지 마라. `docs/` 디렉토리 자체가 없으면 "최신화할 문서 없음"으로 적어라.
   - 문서마다 어떤 절을 어떻게 고칠지 구체적으로 적어라. "문서 업데이트" 같은 막연한 표현을 쓰지 마라.
   - 인수 조건으로 만들지 마라. 중앙 문서 최신화는 인수 테스트와 Review의 검증 대상이 아니다. 문서 내용의 정확성은 Documentation 단계가 코드를 근거로 직접 확인한다.
   - EXPLORE에서 발견한 중앙 문서와 코드의 불일치가 이번 작업 범위 안이면 최신화 대상에 넣어라. 범위를 벗어나면 "범위 밖 문서 과제"에 적어 두고 고치지 마라.
   - 중앙 문서는 `docs/` 아래에 두고 SCM으로 관리한다.
   - `runs/` 아래 기록은 최신화 대상이 아니다. 기록은 그 시점의 사실이므로 고치지 않는다.
   - 이번 작업이 프로젝트의 사실을 바꾸지 않아 최신화할 문서가 없으면 "없음"과 그 이유를 적어라.
7. 인수 조건 문서의 해시를 기록하라. Review 단계가 이 해시로 문서가 바뀌지 않았는지 확인한다.
   ```bash
   sha256sum "$TASK_DIR/01.plan/ACCEPTANCE_CRITERIA.md" > "$TASK_DIR/01.plan/.acceptance_criteria.sha256"
   ```
8. 타임라인을 기록하라.
   ```bash
   node .claude/skills/sdd-workflow/scripts/timeline.mjs mark "$TASK_DIR" plan - end
   ```
9. 사용자에게 산출물 경로, 단위 작업 수, 인수 조건 목록(ID와 한 줄 요약)을 보고하라. `sdd-workflow`에서 호출된 경우 이어서 인수 조건 확인 체크포인트를 진행한다.
10. 체크포인트에서 사용자가 인수 조건 수정을 요청하면 세 문서를 함께 고쳐 추적 관계를 유지하고, 6번의 해시를 다시 기록하라. 체크포인트가 끝난 뒤에는 인수 조건을 수정하지 않는다. 해시 재기록은 7번 명령을 다시 실행한다.

## ACCEPTANCE_CRITERIA.md 템플릿

```markdown
# ACCEPTANCE CRITERIA — <작업 제목>

- 작성: <YYYY-MM-DD HH:MM>
- 이 문서는 Plan 단계 이후 수정하지 않는다.

## 인수 조건
| ID | 인수 조건 | 관련 요구사항 |
|---|---|---|
| AC-01 | <조건>에서 <행동>하면 <기대 결과>이다. | R-01 |

## 요구사항 추적
| 요구사항 | 인수 조건 |
|---|---|
| R-01 | AC-01, AC-02 |

## 범위 제외
- <이번 작업에서 하지 않는 것과 이유>
```

```markdown
# ACCEPTANCE TEST PLAN — <작업 제목>

- 작성: <YYYY-MM-DD HH:MM>

## 테스트 환경
- 실행 경로: <Host OS / Docker>
- 필요 서비스: <PostgreSQL, Paseo 등>
- 환경변수: <테스트에 쓰는 값>
- 증거 형태: <스크린샷 / 명령 출력 / 로그 / DB 조회 결과>

## 테스트 케이스
### AT-01 <테스트 이름>
- 검증 대상: AC-01
- 사전 조건: ...
- 절차:
  1. `<명령 또는 조작>`
- 기대 결과: ...
- 증거: <무엇을 어떻게 남길지>

## AC ↔ AT 매핑
| 인수 조건 | 인수 테스트 |
|---|---|
| AC-01 | AT-01 |
```

## PLAN.md 템플릿

```markdown
# PLAN — <작업 제목>

- 작성: <YYYY-MM-DD HH:MM>

## 목표
<이 계획이 달성하는 것 한두 문장>

## 단위 작업
1. **<단위 작업 이름>**
   - 대상: `<파일·모듈>`
   - 할 일: ...
   - 완료 기준: ...
   - 관련 AC: AC-01
2. ...

## 중앙 문서 최신화
Documentation 단계(`sdd-documentation`)가 Verification Gate 통과 후 수행한다. 이미 있는 문서만 최신화하고 새 문서는 만들지 않는다.

| 문서 | 최신화할 내용 | 근거 (단위 작업 / AC) |
|---|---|---|
| `docs/...` | <어느 절에 무엇을 반영하는지> | 단위 작업 2, AC-03 |

최신화할 문서가 없으면: 없음 — <이유>

### 범위 밖 문서 과제
- <이번 작업 범위를 벗어나 고치지 않는 중앙 문서 불일치>

## AC 추적
| 인수 조건 | 단위 작업 |
|---|---|
| AC-01 | 1, 3 |

## 위험 요소와 대응
- <위험> → <대응>
```

## 완료 조건

- 모든 요구사항이 하나 이상의 AC로, 모든 AC가 하나 이상의 AT와 단위 작업으로 추적된다.
- 모든 AC가 합격/불합격을 판정할 수 있게 쓰여 있다.
- 단위 작업이 수행 순서대로 나열되어 있다.
- Documentation 단계가 최신화할 중앙 문서가 이미 있는 문서만으로 정리되어 있거나, 없다는 판단과 이유가 적혀 있다.
